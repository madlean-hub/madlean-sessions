This type-checks

def mostInteresting : ℕ := 37

Start with the most basic thing a type checker does. We claim mostInteresting has type ℕ, and we hand over the term 37. 37 really is a ℕ, so the term has the type we claimed. That is a complete, if tiny, act of type checking.

This doesn't

/-- error: Type mismatch "not 37" has type String but is expected to have type ℕ -/ #guard_msgs in example : ℕ := "not 37"

Swap the term for a string and the check fails: the term's type, String, isn't the ℕ we claimed, and Lean says so.

This proof checks

theorem one_add_one : 1 + 1 = 2 := rfl

A theorem is checked the very same way. We claim 1 + 1 = 2, and the proof is rfl -- "the two sides are the same once you compute". The kernel reduces 1 + 1 to 2, sees they match, and accepts. Same act of type checking, now at the level of a proof.

This proof doesn't

/-- error: Tactic `rfl` failed: The left-hand side 1 + 1 is not definitionally equal to the right-hand side 3 ⊢ 1 + 1 = 3 -/ #guard_msgs in example : 1 + 1 = 3 := by⊢ 1 + 1 = 3 rfl⊢ 1 + 1 = 3

Claim 1 + 1 = 3 and rfl can't prove it: 1 + 1 reduces to 2, not 3, so the two sides aren't definitionally equal.

What type checking isn't

Notation

set_option pp.notation false in #checkNat : Type ℕ

Lean expands notation first. Put your cursor on the #check: with notation turned off, ℕ shows as Nat -- the symbol we have been writing all along is just surface syntax for the underlying type. +, ∑, ≤, ∫, ℕ, ℝ are all readable notation; the kernel never sees them.

Implicit arguments

set_option pp.explicit true in #checkfun l => @List.length Nat l : List Nat → Nat fun (l : List ℕ) => l.length

You leave the type out; the elaborator reconstructs it. Cursor on the #check: made explicit, l.length is @List.length Nat l -- the hidden Nat is filled in. By the time the kernel sees the term, every implicit argument is spelled out.

Coercions

#checkfun n => ↑n : ℕ → ℤ fun (n : ℕ) => (n : ℤ)

With n : Nat used where an Int is expected, Lean inserts a coercion. Cursor on the #check: the result is fun n => ↑n -- that ↑ is a cast you never wrote. The kernel sees the cast, not your intention to "just use n".

Instance resolution

set_option pp.explicit true in #checkfun a b => @HAdd.hAdd Nat Nat Nat (@instHAdd Nat instAddNat) a b : Nat → Nat → Nat fun (a b : ℕ) => a + b

To make sense of +, Lean searches for an Add instance and plugs it in. Cursor on the #check: made explicit, a + b is @HAdd.hAdd Nat Nat Nat (@instHAdd Nat instAddNat) a b -- the chosen instance instAddNat becomes an invisible argument. Keep that in mind; it can surprise you. We'll come back to it.

Running tactics

theorem append_nil_length (l : List ℕ) : (l ++ []).length = l.length := byl:List ℕ⊢ (l ++ []).length = l.length simpAll goals completed! 🐙 #printtheorem RpyleanExamples.append_nil_length : ∀ (l : List ℕ), (l ++ []).length = l.length := fun l => of_eq_true (Eq.trans (congrFun' (congrArg Eq (congrArg List.length (List.append_nil l))) l.length) (eq_self l.length)) append_nil_length

You write by simp to prove that appending the empty list doesn't change a list's length. Now put your cursor on the #print: that's the term simp actually built. simp found the lemma List.append_nil, applied it, and reified the rewrite as a proof term -- of_eq_true (Eq.trans (congrArg ...)). You would never write this by hand, and you never see it. The tactic's only job was to produce that term; then it vanished. The kernel checks the term, and never knew simp existed.

None of these reach Lean's kernel, which cares about type checking

notation · implicits · coercions · instances · tactics

That's everything that happens after the above "finish". The kernel's job is well enough contained that one can write their own!

What does it do?

A little program whose job it is to look at all the declarations in Lean's environment and check each thing against its purported type.

Building one makes the real questions concrete. There are many independent re-implementations of Lean's kernel -- the Lean kernel arena collects them, each checking the same exported terms. Why do this?

  • you get a second opinion on Lean's answers

  • to learn about Lean's behavior

  • to learn about its type theory

  • for fun?

  • the kernel stops being magic

Given a fully elaborated term...

Does this term really have this type? -- re-checked from scratch. For theorems and definitions, infer the type, check it is definitionally equal to the one we need.

One question, asked over and over: independently confirm the term inhabits the type -- no notation, no search, no tactics. The whole point is that you only have to trust this one small piece.

A proof is a term, too

def modusPonens {p q : Prop} (h : p → q) (hp : p) : q := h hp

Curry-Howard, for mathematicians: a proposition is a type, and a proof of it is a term of that type. So "a valid proof of P" means exactly "this term has type P" -- checking a proof and type-checking a term are the same activity, which is why one small kernel handles both. Here modus ponens -- from p → q and p, conclude q -- is literally h applied to hp, function application, checked like any other.

Lots and lots of terms...

A handful of shapes:

  • a variable (bound or free)

  • a sort -- Prop, Type, ...

  • a constant -- a reference to a declaration: Nat, List, a theorem, ...

  • a literal -- 37, "hello"

  • an application f a

  • a fun or a ∀

  • a let, or a projection

There aren't many kinds of term, and the whole kernel is just "how to handle each shape." One subtlety worth saying aloud: an inductive type like Nat or List, its constructors, and its recursor are not term shapes -- they live in the environment as declarations, and a term just refers to them as constants. So the whole vocabulary really is this: variables, sorts, constants, literals, application, functions and function-types, let-bindings, and projections -- essentially all of mathematics, fully spelled out.

How rpylean checks a theorem

class W_Theorem(W_DeclarationKind):

    def type_check(self, type, tc):
        type_type = type.infer(tc)
        type_type_whnf = type_type.whnf(tc)
        if not isinstance(type_type_whnf, W_Sort):
            return W_NotASort(...)
        if not type_type_whnf.level.eq(W_LEVEL_ZERO):
            return W_NotAProp(...)
        val_type = self.value.infer(tc)
        if not tc.def_eq(type, val_type):
            return W_TypeError(...)

That's the whole thing. Four real lines of work. One: infer the type's own type. Two: it must be a Sort -- a genuine type. Three: its level must be zero, i.e. it must be a Prop, because this is a theorem -- universes are how the kernel separates a proposition from a type: Prop is level 0, Type is level 1, and so on. Four: infer the proof's type and check it's definitionally equal to the claimed type. infer, whnf, def_eq -- exactly the three moves from the previous slide. Everything else on screen is just which error to report when a check fails. (I trimmed those error arguments to ... here.)

What an export looks like

{"in":1,"str":{"pre":0,"str":"Nat"}}      -- name #1  = Nat
{"il":1,"succ":0}                          -- level #1 = 0 + 1
{"ie":0,"sort":1}                          -- expr  #0 = Sort 1  (Type)
{"const":{"name":1,"us":[]},"ie":1}        -- expr  #1 = the constant Nat
{"def":{"name":..,"type":..,"value":..}}   -- a declaration

The export is line-based: four tables -- names, universe levels, expressions, declarations -- each row referenced later by an integer index. Big terms stay small because everything is shared by index. rpylean's parser turns each line into one of those term shapes from the zoo.

rpylean accepts the good ones

$ rpylean check basicDef.ndjson
basicDef ... OK
summary: 1/1 decls checked

Run a good case through rpylean and it passes: the value's type matches the declared type, def_eq holds, and nothing is returned. That's the happy path straight through the code on the previous slide.

...and catches the bad ones

$ rpylean check nonPropThm.ndjson
theorem nonPropThm : Prop := ∀ (x : Prop), x
                     ^^^^

                       Type
                     but the type of a theorem must be a proposition (Prop)

Now a bad theorem: its type is Prop, whose sort is Type -- not level zero, so it isn't a proposition. That's exactly the level.eq(W_LEVEL_ZERO) check on the previous slide failing and returning W_NotAProp; the message is rpylean rendering that error. Real output, both cases from the arena tutorial.

One real question: are two terms equal?

To decide it, the kernel reduces both sides and compares. A few moves:

Type-checking comes down to this. To check f a, you check a's type is the one f expects; to accept rfl : x = y, you check x and y are the same. And "equal" doesn't mean equal on the page -- it means equal after computing, as far as both sides will go. That's definitional equality, the kernel's real work, and to decide it the kernel reduces. There are only a handful of moves -- one per slide.

Beta

Apply a function.

(fun x => b) a becomes b, with a in for x.

(fun n => n * n) 3 ⟶ 3 * 3

Beta reduction: the most familiar move. A function applied to an argument substitutes the argument into the body -- here, squaring at 3. This is just "plug in".

Delta

Unfold a definition by its name.

double 3 ⟶ 3 + 3

Delta reduction: replace a defined constant with the term it was defined to be. This is how double 3 becomes 3 + 3, and how the kernel sees through abbreviations when it needs to.

Zeta

Substitute a let.

let n := 5; n * n ⟶ 5 * 5

Zeta reduction: a let n := v; body becomes body with v in for n. Like beta, but for local definitions.

Iota

Run a recursor -- pattern-match on a constructor.

match 3 with | 0 => 0 | n + 1 => n ⟶ 2

Iota reduction: this is how recursion and induction actually compute. Here 3 is Nat.succ 2, so the n + 1 branch fires and hands back 2 -- that's the predecessor function. The same move is what makes 2 + 2 reduce to 4.

Projection

Pull a field out of a structure.

(3, 4).1 ⟶ 3

Projection reduction: given a constructed structure, extract one of its fields. Here, the first coordinate of the point (3, 4). Cheap, but its own kind of step.

Proof irrelevance

Any two proofs of the same Prop are equal.

Two proofs of Prime 7 are interchangeable.

A special rule, not a reduction: if two terms are proofs of the same proposition, the kernel treats them as equal without comparing them. However you proved 7 is prime, the kernel won't distinguish your proof from any other -- only that the proposition holds.

Reductions compose

double 3 ⟶ 3 + 3 ⟶ 6

delta, then iota

Real checking chains these moves. double 3 unfolds by delta to 3 + 3, then the additions run by iota down to 6. The kernel just keeps applying moves until nothing changes -- then compares.

Checking other terms...

An axiom has no value

It's assumed -- never checked.

An axiom stores a name and a type but no proof term. The kernel never checks it; it's simply believed. Useful and necessary -- and, as we'll see, a place where trust can leak.

Trust: "Proof" is not the same as "Proves what you meant"

Now the sharp edge. The kernel guarantees "this term has this type." It does not guarantee the type is the statement you intended. Remember instance resolution from the very start? Watch what it can do.

Suppose, far away, one line

local instance instNatAdd : Add ℕ := ⟨Nat.mul⟩

Imagine somewhere above -- maybe in an import -- a single line quietly redefines + on ℕ to mean multiplication. This is exactly the instance search we met earlier, now with a surprising answer in the database. Nothing else changes. Watch.

It says 1 + 0 = 0

theorem oneAddZero : 1 + 0 = 0 := by⊢ 1 + 0 = 0 rflAll goals completed! 🐙

Here is a theorem. It reads 1 + 0 = 0, and Lean accepts it. Put your cursor on the +. Notice the instance from the previous slide is nowhere here -- it's hidden in an invisible argument.

The kernel checked Nat.mul 1 0 = 0

Instance resolution picked our redefinition, whose add is Nat.mul. So the proposition actually formed and certified is Nat.mul 1 0 = 0 -- which is true, 1 * 0 = 0, so it passes. The kernel was not fooled and not wrong. It certified a true statement -- just not the one you'd read off the page. That gap is the whole reason to understand the kernel.

The same moves -- now ours

  • infer a term's type

  • reduce to normal form (beta, delta, ...)

  • check two terms are definitionally equal

For each declaration: infer the value's type, then check it's definitionally equal to the declared type -- using exactly the reductions we covered. The same algorithm a real kernel runs, just one we can read and poke at.

A theorem is a type and a proof

theorem two_add_two : 2 + 2 = 4 := rfl

the type 2 + 2 = 4 · the proof rfl

Take a concrete theorem. It has exactly two parts: a type -- the proposition 2 + 2 = 4 -- and a value, the proof rfl. To accept it, rpylean must confirm the proposition really is a proposition, and that the proof really has that type. Watch how little code that takes.

A stray axiom is just believed

sorry is one of them.

If a proof rests on an axiom -- including sorry, which is an axiom -- the kernel happily certifies it. The proof is valid; its foundation might not be one you'd endorse.

native_decide skips the kernel

Some tactics defer to compiled native code that the kernel never re-checks. Fast, but it widens the circle of things you're trusting beyond the kernel itself.

#print axioms

What does my proof ultimately rest on?

The practical takeaway: #print axioms myTheorem tells you exactly which assumptions your proof depends on. It's the cheapest honesty check you have.

Can we prove a kernel correct?

lean4lean does -- in Lean itself.

There's a project, lean4lean, that verifies Lean's kernel inside Lean. Which opens its own wonderful rabbit hole about what it means to trust a system that checks itself.
